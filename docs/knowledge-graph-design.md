## 0. 一句话

**默认是一棵「分类树」：节点是概念，父节点是它所属的分类（领域 → 子领域 → 概念）；没有合适分类时，就新建一个父节点安放它；树上只画「所属」这一种边。其它关系（前置 / 应用 / 相关 / 共现）平时不画，只有聚焦某个概念时才临时展开它最直接的那几条，点完收起。**

这张树只做两件事：**看见「我的知识分成哪几块、每块下面有哪些概念」，以及从任何一个节点跳回产生它的笔记片段。** 它不回答「我掌握得怎么样」，也不排复习计划（§2.2）。

> 和 v1.0 的区别一句话：v1.0 把「关系」当骨架（先有关系才画得出图）；v1.1 把「归属」当骨架（先有分类就有图），关系变成聚焦时才出现的细节。这是从用户反馈里得到的修正，不是推倒重来：派生、溯源、确定性布局、文件为真相这些底层设计原样保留。

## 1. 为什么做，以及为什么改掉旧结论

### 1.1 需求

用户在 2026-11-02 明确要求：知识点已经能从笔记里抽出来（P0 已落地），下一步要「把这些知识点汇成网络（分层图），通过这张网络快速查看知识体系并通过节点定位相关内容」，并把「知识体系」称为**项目的核心**（pluginization-plan 第 2 条原话）。

这和知识库一期「列表 + 搜索」是互补关系，不是替代：

| 场景 | 一期（列表/搜索） | 这一期（分类树） |
|---|---|---|
| 我知道要找什么 | 搜「RAG」→ 命中概念/笔记 | 同样能搜，搜索框仍是入口 |
| 我想看看「我这块学到哪了」 | 只能一列列翻概念 | 一眼看到领域 → 子领域 → 概念的分层和数量 |
| 我读到一个概念，想知道它和什么有关 | 只能看单条概念详情的 8 个 related | 聚焦它，直接看到最直接的关系（且不污染全局） |
| 我想从概念回原文 | 概念详情 → 命中片段 → 打开笔记 | 同一套追溯链路，从树上某个节点发起 |

### 1.2 旧结论与这次变更

[knowledge-base-draft.md](knowledge-base-draft.md) 当时明确写了「不画全局知识图」（§0/§7），§5 的理由是：

1. 现有 UI 是 12 栏卡片 + 挂载点体系，力导向图塞不进去；
2. 查东西靠搜索/列表，不靠看图；
3. 真要做图，放在知识页内用宿主 Canvas 画「局部图（当前概念 ±1 跳）」，不进插件卡片词汇表。

这次**只推翻第 1、3 条的范围结论，保留第 2 条的内核**：

| 旧顾虑 | 现在的事实 | 结论 |
|---|---|---|
| 12 栏卡片塞不进图 | 图不放在插件卡片里，是**知识页内的第三视图**（整页可用，页面本来就不套 1120dp 宽），不进 `UiNode` 词汇表 | 推翻范围限制 |
| 力导向图不可控 | 我们**不用力导向**：分类树是确定性 tidy-tree 布局（§4），同输入同输出、可纯函数测试 | 推翻技术前提 |
| 查东西靠搜索 | 仍然靠搜索；图是**第二入口**，且图里保留搜索定位 | 保留：图不替代搜索 |
| 只做局部图 | 用户要的是「体系」；只做 ±1 跳看不到结构。全局分类树 + 聚焦局部关系同时提供 | 推翻 |
| 图不该进插件词汇表 | 知识页本来就是宿主硬编码 Compose 页面（不是插件、无挂载点） | 保留：不碰内核 |

另外两条边界沿用调研结论：

- **不做全量 GraphRAG**（`docs/research/tech.md` §1.4：个人语料收益低、成本随语料增长；Graphiti 还需 Neo4j）。我们只用「概念 + 归属 + 少量聚焦关系」的轻量图，关系靠笔记派生 + 少量 AI 建议。
- **不把图当掌握度**：节点大小只编码「出现多少」，不编码「学会多少」（§3.2、§5.4）。

### 1.3 2026-11-02 晚间反馈：为什么从「关系图」改成「分类树默认视图」

v1.0 的示意图（`page-mockup.svg` 第一版）画的是：横向领域岛 + 纵向依赖层 + 四种关系边 + 待连线带。用户看完的反馈是：

> 「现在的图链接太乱了，我想把这些点都只保留最直接的关系，没有合适的节点就创建父节点，形式可以类似分类进行划分，那么父节点就是它的所属；其余的关联都只在聚焦于该点的时候显示。」

这里其实指出了一个设计错误和两个正确方向：

| 问题 | v1.0 的做法 | 为什么不行 | v1.1 的修正 |
|---|---|---|---|
| 默认画了太多边 | 共现、相关、前置、应用、AI 建议全部可画，靠筛选开关控制 | 用户第一次打开不知道关哪个；边一多就糊，图的「结构感」被噪声淹没 | 默认**只画所属边**（分类树），其它边**只在聚焦时出现** |
| 前置关系太稀疏，撑不起骨架 | 用前置/应用关系算依赖层，没有关系时整图塌进「待连线带」 | 大多数笔记里根本不会写「A 是 B 的前置」；没配 AI 的用户打开就是一堆散点 | 骨架改用**分类归属**：AI/用户建分类，天然覆盖全部概念；不依赖关系是否被写出来 |
| 关系仍然有价值，不该删 | 直接拿掉会让「为什么这两个概念有关」无处可看 | 关系是导航线索，只是不该常驻 | 聚焦某节点时展开它的**直接关联**，点空白处收起；关系数据原样保留 |

所以 v1.1 的分工是：

- **分类树负责「体系」**：领域、子领域、概念的数量与归属，是用户要的「快速查看知识体系」；
- **聚焦负责「关联」**：选中一个概念，才显示它最直接的前置/应用/相关（最多 12 条），其余节点淡出；背景点击/Esc 恢复；
- **旧的依赖分层不删**：它被降级为**可选的「体系视图」**（G2），给「关系写得足够多的重度用户」用，算法与原型验证原样保留（§4.7、§9.3）。

### 1.4 为什么现在做

- 数据已齐：`ConceptSummary`（名字/笔记数/提及数/最近更新）、`ConceptDetail`（每个概念的命中片段 + start/end 偏移）都已经从文件实时算好；分类树只是把「概念集合」按归属重新排列（§3.1），**不需要新的数据采集**；
- 定位链路已通：`pendingReveal`（笔记 + 正文区间）→ 编辑器选中并滚动，树上点节点可以直接复用（§5.7），不需要新的定位机制；
- 布局可以做成纯函数：笔记 → 节点/分类树（构建）→ 坐标（tidy-tree 布局）三段全是不碰 Compose 的 Kotlin 纯逻辑，测试容易（§10.1）；分类树没有环、没有力导向，比 v1.0 的依赖分层更简单、更稳；
- 分类归属是「零关系也能出图」的兜底：第一次用、没配模型、笔记里没写前置，用户仍然能看见自己的知识分成哪几块——这正是「知识体系是核心」的最低可交付；
- 等计划↔概念打通后再做图，会同时被两个未完成面拖住；先把「分类树 + 聚焦」这一步做完，第 3 条「能力地图」才有地方挂（§9.3）。

### 1.5 2026-11-03 晚第二次反馈：画布再简化（当前 v1.2）

G0 落地当天晚上，用户看过真实截图后提了三条（原话「目前网络仅作简单的分类链接、父子链接即可……聚焦可以来点动效，聚焦节点，弹出节点信息，节点信息可以专门做一个小浮窗来承载……深度不需要预制，交给 AI 做就行了，像建一颗虚实结合的树」）。v1.2 据此把「分区画布 + 右栏详情」再简化一遍：

| 反馈 | 修正 | 落在 |
|---|---|---|
| 画布只保留最直接的关系 | 画布只剩**节点 + 父子连线**；分类是**虚节点**（空心、虚线边），概念是**实节点**（实心）；去掉计数、AI 徽标、定义、芯片网格等一切附加信息 | §4.9、§5.11 |
| 其它信息别堆在图上 | 点击节点：其它节点淡出、选中节点轻微放大（spring 动效），节点旁弹出**小浮窗**承载定义 / 所属路径 / 来源片段 / 直接关联 / 操作；**删除右栏 320dp 详情面板** | §4.9、§5.11 |
| 深度不要预制 | 删除「分类深度 1–5」「分类默认折叠」等预制开关；**深度由 AI 归类时决定**（G1）。纯逻辑只保留 32 层安全上限（防坏数据/死循环），UI 不暴露 | §3.3、§9.2 |

保留不动：分类树是骨架、确定性布局、两个 json（`graph.user.json` 权威 / `graph.cache.json` 缓存）、关系边只在聚焦时出现、AI 只建议、不碰内核、不新增挂载点。

> 为什么这么改：画布是**导航器**不是仪表盘——一眼先看清「分成哪几块」，细节按需在浮窗里展开；深度也不是用户该预填的参数，它本身就是 AI 归类要做出的判断。

### 1.6 2026-11-03 深夜第三次反馈：虚节点 + 拖动链接（当前 v1.3）

v1.2 交付后用户指出：「实节点不一定存在上级节点」——即「新建上级分类 → 再移动」这个流程默认了「先想好父类名字、再挪进去」，但更自然的是**先在画布上放一个空节点，再把它拖到该归属的位置**。原话：「不如单独做一个添加虚拟节点的入口，鼠标拖动到节点上自动将该节点作为子节点进行链接，可以手动重命名虚节点，AI 整理也可以，因此 AI 整理就是创建节点、命名节点、链接节点，然后将知识点（实点）在图中按『类』维护」。

| 反馈 | 修正 | 落在 |
|---|---|---|
| 实节点不一定有上级 | 工具条加「＋ 虚节点」（唯一入口，左栏不再重复）：一键在画布上新建一个空的分类节点（名字默认「新分类」「新分类 2」…，可改名），不预设它放哪 | §4.9、§5.5、§5.11 |
| 拖动建立父子链接 | 从分类节点按下拖动：拖到任意节点上松手，那个节点就被收为该分类的子节点（概念→`assignConcept`，分类→`moveCategory`，移动整棵子树）；落点非法（自己/后代/祖先）不高亮、松手不生效；拖空白仍是平移画布 | §4.9.1 |
| 手动重命名虚节点 | 浮窗里改名（原有能力），改名不影响 id 与归属 | §5.11 |
| AI 整理 = 建节点/命名/链接 | G1 的 AI 建议从「只报一个 `categoryPath` 字符串」改成**图操作三件套**：`createCategory(name,parent)` → 按建议命名 → 把概念/分类链接到父节点；用户确认后才写 `graph.user.json`。深度与层级由 AI 在操作序列里体现，不是 UI 参数 | §6.1、§9.2 |

为什么这么改：分类树的本质是「按类维护知识点」，那么**建类、命名类、把东西挂进类**就应该是同一套直接操作；先建再移动只是这套操作的一个特例。AI 整理也只是替人执行同一套操作（带确认门），不是另一条路径。

## 2. 目标与非目标

### 2.1 必须做到（G0+G1 验收，逐条可验）

| # | 能力 | 验收方式 |
|---|---|---|
| 1 | 知识页出现第三个视图「网络」，与「笔记 / 概念」平级切换；视图选择、相机（缩放/平移）、展开状态、选中节点在页内切 tab、离开页面再回来都保留 | 手点 + 截图 |
| 2 | 默认视图是一棵分类树：概念是叶子，父节点是分类；**默认只画所属边**，不画任何前置/应用/相关/共现边；分类节点可折叠/展开，折叠后显示「N 个概念」 | 固定 fixture 断言布局节点/边集合：默认边集 == 树边 |
| 3 | 每个概念有且只有一个所属分类（单父）；分类可多层嵌套（领域 → 子领域 → 概念，深度上限 5）；没有合适分类时可新建父节点，概念可移动/改名/合并分类 | 单测（树不变量 + CRUD 语义） |
| 4 | 没有分类时，概念进「未分类」区并明确提示；未分类区不是错误，是「待归类」的工作队列 | 截图 + 单测 |
| 5 | **聚焦**：点概念 → 显示它最直接的关系（前置/应用/相关，最多 12 条），邻居高亮、其余节点淡出、画布上画出这少量关系边；点空白/再次点击/Esc 收起；关系不常驻 | 单测（聚焦边集合 / 上限 / 收起）+ 手点 |
| 6 | 点节点 → 右侧详情（所属分类面包屑 / 定义 / 直接关联 / 来源笔记与片段）；点来源 → 打开对应笔记并选中命中片段（复用 `pendingReveal`）；面包屑可点回父分类 | 手点 + 单测定位参数 |
| 7 | 分类节点详情：名称/路径/数量、子分类与概念列表、改名为「移动到…」「合并到…」「删除（子项回未分类）」；AI 新建的分类有明确来源标记，可确认/改名/删除 | 手点 + 单测 |
| 8 | 搜索框能定位节点（自动展开祖先 + 高亮 + fit）；滚轮缩放、拖拽平移、适应全图；折叠状态的树仍可键盘操作搜索/列表 | 手点 |
| 9 | 「让 AI 归类」：手动触发、按批显示进度、可取消、结果写缓存、失败降级不挡图；AI 归类建议（含自动新建的父分类）可逐条确认/改名/删除，删掉的不会因为再次整理复活（墓碑） | mock LLM e2e + 手点 |
| 10 | 不写坏知识真相：笔记 Markdown 文件一个字节不变；除 `knowledge/graph.user.json`、`knowledge/graph.cache.json` 外不新增其它持久文件（`.bak` / `.bad-<ms>` 是这两个文件的备份/留档，可随时删）；删掉这两个 json 后分类树能重建（只丢用户分类与缓存） | 单测（文件清单/笔记 hash 不变） |
| 11 | 性能：500 概念 / 5 层分类折叠展开、聚焦切换无明显卡顿；2000 节点自动进入折叠/聚合视图仍可操作 | 观察 + 布局耗时单测 |
| 12 | 无模型配置、无网络、AI 报错时，分类树照常显示（手动分类 + 未分类区），并给出下一步提示 | 断网/空 key 跑 |

### 2.2 明确不做

| 不做 | 原因 |
|---|---|
| 掌握度、正确率、遗忘曲线、复习调度、打卡/经验值 | 一期已拍板；这是另一个产品线（间隔重复引擎），不是图能解决的 |
| 力导向/物理模拟布局 | 结果不稳定、不可测试；用户每次看到的位置都不一样，违反「知识体系要稳定」 |
| **多父 / 多重继承（一个概念属于多个分类）** | 分类树单父才干净；多父会立刻回到「链接很乱」的老问题。跨领域概念用「移动到更合适的分类」解决；确实需要跨块关联时用聚焦关系表达（G1/G2 的 RELATED 边） |
| 默认常驻展示全部关系（前置/应用/相关/共现） | 用户明确要求「其余关联只在聚焦时显示」；常驻等于回到 v1.0 的糊图 |
| 全量 GraphRAG（社区检测 + 社区摘要 + embedding） | 调研结论不划算；个人几十万字语料用「概念 + 分类 + 少量关系」够了 |
| embedding / 语义相似度边 | 要引模型与向量库；分类归属 + 共现 + AI 关系已经能覆盖「串联」需求 |
| 图编辑模式（拖节点改坐标、自由画布/白板、拖拽画边） | 坐标是算法产物，用户改坐标没有语义；分类移动走「移动到分类」对话框，不靠拖拽 |
| 双链编辑器 / 块引用渲染 | 现在只有 `[[概念]]` 标记，双链是编辑器大改（一期 §7 已排除） |
| 跨端（Android/iOS） | 桌面优先；数据格式与算法不依赖平台，但 UI 只在 desktop 落地 |
| 多用户 / 云同步 | 单机文件 |
| 计划节点完成自动点亮概念（G2 才做） | 计划后端与知识库目前零连接（`plan_unit` 无 concept 列）；「执行过 ≠ 记过」，先手动/笔记驱动，关联设计见 §6.8 |
| 导出 PNG/SVG、分享 | 需求没提；G2 可选 |
| 插件扩展点（第三方贡献节点/布局） | 图是宿主页面；等知识库拆成 `:features:knowledge` 后再谈 |

### 2.3 用户旅程（设计要服务的三个真实场景）

1. **「我学过 RAG 这块，但记不清整体了」**：打开知识页 → 切「网络」→ 看到「检索与生成」分类下挂着向量检索/分块/重排/RAG 评测等概念，数字告诉我每块有多少 → 点 RAG 概念，聚焦展开它直接关联的 3 条前置 → 点某条来源，跳回原文。
2. **「这两个概念是不是一回事 / 有没有关系」**：搜 A → 自动展开祖先并定位 → 聚焦 A，看它直接关联里有没有 B（没有就表示最近关系里没有）→ 去 B 的笔记确认 → 回到树上把 A 移到更合适的分类（或 G1 加一条 RELATED）。
3. **「我的知识体系缺哪块」**：扫一眼树 → 发现「评测」分类下只有 2 个概念、很多概念堆在「未分类」→ 点「让 AI 归类」，它把未分类概念建议到现有分类或新建父分类 → 用户确认/改名/合并 → 树变整齐；不配模型时手动建分类同样能完成这一步。

## 3. 数据模型

### 3.1 三类事实，三种权威

图上的信息只允许来自三种地方，优先级从高到低：

| 类别 | 存在哪 | 权威 | 丢了会怎样 |
|---|---|---|---|
| **笔记派生**（概念节点、节点统计、共现/显式链接等「候选关系」） | 不落盘，每次从笔记文件现算 | 笔记 Markdown 是唯一真相 | 删掉重算，结果一致 |
| **分类归属与用户策展**（分类树、概念→分类的归属、改名/移动/合并、加/删关系、删除墓碑） | `knowledge/graph.user.json` | 用户，最高优先级 | 丢了退回「纯派生 + AI 建议」状态，树仍在（概念全部进未分类区） |
| **AI 建议**（AI 新建的分类、AI 归类、笔记内关系、全图关系） | `knowledge/graph.cache.json` | 建议者，最低优先级，可整体丢弃 | 丢了重新点「整理」，不影响其它 |

这条优先级解决两个已有缺口：一是「手动删掉的概念会被 AI 重新抽回来」（knowledge-base-draft §10 已知缺口）——图里的删除用**墓碑**（§6.7）；二是「AI 改一次用户就丢一次策展」——用户文件与 AI 缓存物理分开，AI 永远不写 `graph.user.json`。**AI 新建的分类只是建议**：默认视图会显示（否则用户看不到 AI 帮他做了什么），但带「AI」徽标、可一键改名/移动/删除；用户确认后写入 `graph.user.json` 变成正式分类。

### 3.2 节点：概念节点与分类节点

```kotlin
internal enum class GraphNodeKind { CONCEPT, CATEGORY }
internal enum class NodeOrigin { DERIVED, USER, AI }   // 概念恒 DERIVED；分类是 USER 或 AI

/** 图上的一个节点。概念节点全部字段从现有数据现算；分类节点来自用户/AI 的分类树。 */
internal data class GraphNode(
    val key: String,              // 概念：conceptKey（normalize + lowercase）；分类：categoryId（"c_" + 8 hex）
    val kind: GraphNodeKind,
    val name: String,             // 概念：展示名（同 ConceptDetail.display）；分类：用户/AI 起的名字
    val definition: String?,      // 概念：concepts.json 的定义；null = 还没写。分类：null
    val noteCount: Int,           // 概念：出现在几篇笔记的 frontmatter 里；分类：0（数量现算）
    val mentionCount: Int,        // 概念：正文出现次数；分类：0
    val firstSeenAt: Long,        // 概念：最早一篇相关笔记的 created（毫秒）；分类：创建时间
    val lastSeenAt: Long,         // 概念：最近一篇笔记的 updated；分类：最近修改时间
    val frontmatterOnly: Boolean, // 概念：只在 frontmatter 标注、正文没出现
    val parentKey: String?,       // 概念：所属分类 id；null = 未分类。分类：父分类 id；null = 根分类
    val origin: NodeOrigin,       // 概念 DERIVED；分类 USER（用户建的）或 AI（AI 建议/自动建的）
    val description: String?,     // 分类：一句话说明（AI 可给，用户可改），≤40 字；概念：null
    val confirmed: Boolean,       // 分类：AI 建的且用户还没确认 → false（显示 AI 徽标）；其余 true
    val sortOrder: Int,           // 同级排序种子（G0 默认 0，按名字；G1 支持上移/下移）
)
```

**概念节点**的集合 = `KnowledgeStore.conceptIndex()` 里的概念（一期 2026-11-03 起，它由正文里的 `[[原文 => 概念名]]` 标注重算成 frontmatter `concepts:` 缓存，见 `synchronizeConceptMembership`）。正文里出现但没被标注/登记的词不是节点——「点亮」的定义沿用一期：**被标注入索引才算亮**。

> 不做「掌握状态」字段。将来若接计划（G2），用**独立的状态叠加**（节点外圈环），不改节点语义。

**节点键沿用一期 `conceptKey`，图里不另起一套归一化。** 一期 `normalizeConceptName` 已经做了空白折叠、trim、把中英文逗号换成空格、`take(40)`，`conceptKey` 再 lowercase，所以「RAG / rag / Rag」在现有索引里本来就是同一个概念。图**不额外做 NFKC/全半角/去零宽字符归一**——那会让图节点键和 `conceptIndex` 的键对不上，等于在 UI 层偷偷分裂出一套索引；这类差异留给 G2 的「合并两个已存在概念」显式处理（用户看得见、可撤销）。展示名取一期 `ConceptDetail.display`（最近更新那篇笔记的写法）。**一期 2026-11-03 起 `ConceptMetaStore` 有别名（`ConceptIdentity.aliases`，经 `conceptIdentityKey` 参与匹配/高亮/检索），别名只作为匹配入口、不单独成节点**——图仍是一个规范概念一个节点，别名解析交给一期。

> 分类节点的 id 与展示名分开：**id 在创建时生成一次，之后改名不换 id**（否则所有归属要跟着迁移，容易丢）。分类的「路径」= 从根到它的名字用 `/` 连接，是给人看的面包屑和 AI 提示词里的定位，不是机器键。

### 3.3 分类树：单父、可嵌套、可创建、可移动

> **v1.2 深度口径**：UI 不再预制分类深度（没有「分类深度 1–5」开关，也没有默认折叠深度）；深度由 AI 归类时决定（G1，§9.2）。纯逻辑保留 `MAX_CATEGORY_DEPTH = 32` 作为防坏数据/死循环的安全上限，正常使用远碰不到，错误文案只在坏数据时出现。

分类树是第二期唯一的**结构骨架**。规则共 7 条，全部可在纯函数里断言（`KnowledgeGraphTaxonomy.kt`）：

1. **单父**：每个概念最多有一个 `parentKey`（指向分类）；每个分类最多有一个父分类。没有父分类的概念进「未分类」区；没有父分类的分类是根分类。多父明确不做（§2.2）。
2. **只能分类装概念，不能概念装分类**：`parentKey` 必须指向 `kind == CATEGORY` 的节点；分类的父必须也是分类。
3. **无环**：沿 `parentKey` 上溯必须在有限步到达 `null`；深度上限 5（根计 1）。超深或成环的条目在构建时**丢弃并进「未分类」**（不崩、不静默改用户数据，构建后提示「有 N 条分类归属不合法」，见 §5.9）。
4. **AI 可以新建父节点**：归类时如果现有分类都不合适，AI 直接给一个「新分类路径」（如 `系统设计/可观测性`）；系统在合并阶段**创建缺失的分类节点**（origin=AI, confirmed=false），并把概念挂到最末一层。用户确认后转正；不确认也可以直接用，只是带 AI 徽标。
5. **同名约束**：同一个父分类下不允许两个同名子分类（忽略大小写与空白）；不同父下可以有同名分类（路径不同，合法）。概念名与分类名允许重合，但界面上分类用「文件夹」样式、概念用「圆角叶子」样式区分。
6. **删除分类**：删除时其子分类上移到被删分类的父级、概念回到「未分类」；写一条墓碑（§6.7），AI 下次不会原样重建这个分类。删除前弹确认，列出「将移出 N 个概念 / 上移 M 个子分类」。
7. **合并分类**：把 A 合并到 B（B 必须同父或任意已存在分类）：A 的子分类与概念全部改挂 B，A 的 id 记进 `mergedInto` 映射（`c_old → c_new`），旧 id 在读取时自动解析到新 id；写墓碑。用于收拾 AI 造得太细的分类（「RAG 检索」与「检索增强生成」合并）。

未分类不是「错误」：它是**待归类工作队列**。默认视图把未分类概念收在画布默认展开范围之外的「未分类」区（若为空则不显示）；左栏统计常驻显示「未分类 N」，点它 fit 到该区。没有分类时整棵树只有未分类区 + 引导横幅（§5.8）。

### 3.4 关系边：只有聚焦时才出现

关系不再参与结构，也不再默认绘制；它只在聚焦某个概念时临时展开。数据形状沿用 v1.0（已验证过一轮审查）：

```kotlin
internal enum class GraphEdgeKind {
    PREREQUISITE, // A 是 B 的前置（先 A 后 B）；有方向
    APPLIES,      // A 被用于 B / B 是 A 的应用；有方向（from 是基础侧）
    RELATED,      // 相关；无方向
    CO_OCCUR,     // 共同出现；无方向，弱关系，聚焦时默认不显示（可开）
}

internal enum class GraphEdgeSource {
    EXPLICIT,  // 笔记里写了 [[A]] / [[B]] 且同段出现
    HEURISTIC, // 同段/相邻顺序共现推导
    AI,        // AI 建议（笔记内抽取 or 全图补全）
    USER,      // 用户手动加
}

internal data class GraphEvidence(
    val noteId: String,
    val start: Int,   // UTF-16 偏移；-1 = 该概念只出现在 frontmatter
    val end: Int,
    val snippet: String, // ≤120 字，命中行截取
)

internal data class GraphEdge(
    val fromKey: String,
    val toKey: String,           // RELATED/CO_OCCUR 无向：按 key 字典序规范化，保证同一条边只有一个表示
    val kind: GraphEdgeKind,
    val source: GraphEdgeSource,
    val confidence: Float,       // 0..1；只用于排序/强弱，不当概率
    val evidence: GraphEvidence?, // 确定性边必有；全图 AI 边可以没有（它就是「AI 推测」）
    val reason: String?,         // AI 的一句话理由 / 用户备注；≤40 字
    val createdAt: Long?,        // 用户/AI 边的创建时间（时钟注入）；确定性派生边与缓存回读为 null
)
```

三条硬规则（沿用 v1.0，审查过）：

1. **无向边只有一个方向**：`RELATED`/`CO_OCCUR` 存之前把 `(fromKey, toKey)` 按字典序排列，否则 A-B 和 B-A 会出现两条；
2. **证据能落地**：确定性边必须带 `evidence`（noteId + 偏移 + 片段）。全图 AI 边可以没有证据，但必须在详情里显示「AI 推测，无原文依据」；
3. **边不重复**：同 `(from,to,kind)` 只保留一条，优先级 `USER > AI > EXPLICIT/HEURISTIC`；`PREREQUISITE` 与 `APPLIES` 同向撞车时保留 `PREREQUISITE`（更具体）。

**分类树边不是 `GraphEdge`**：父子关系存在 `GraphNode.parentKey` 里，不参与上面的边合并，也不受墓碑/优先级影响——否则「所属」这个唯一骨架会被关系逻辑污染。画布上树边也不画箭头（用嵌套框和引导线表达归属）。

### 3.5 派生关系：从笔记到「聚焦候选」

全部使用现有 `ConceptMatch` 的匹配函数（`conceptHits` 同位置最长优先、ASCII 词边界、中文子串），不新写匹配逻辑。输入：每篇笔记的 `body` + `concepts`。这些关系**只用于聚焦**，不影响分类树。

| 边 | 何时生成 | kind/source | confidence | 证据 |
|---|---|---|---|---|
| 同段共现 | 同段落块内按出现顺序相邻的两个概念 | `CO_OCCUR` / `HEURISTIC` | 0.5 | 段落块首行片段 |
| 跨段相邻 | 同笔记内首次出现顺序相邻、但不同段 | `CO_OCCUR` / `HEURISTIC` | 0.25 | 先出现那条的命中行 |
| 显式链接 | 同段内出现两个 `[[…]]` | `RELATED` / `EXPLICIT` | 0.8 | 该段片段 |
| AI 笔记内关系 | 见 §6.2（必须有原文证据） | `PREREQUISITE`/`APPLIES`/`RELATED` / `AI` | 0.5–0.7 | 原文引用 |
| 全图 AI 关系 | 见 §6.3（手动触发，无原文证据） | `PREREQUISITE`/`APPLIES` | 0.4–0.6 | `null` |
| 用户关系 | 用户手动加（G2） | 任意 / `USER` | 1.0 | 可填一句备注 |

规则细节：

- **段落块** = 按空行切分；标题行单独成块；**跳过 fenced code 与 `:::ai` 块**——直接复用一期 `KnowledgeNote.forEachPlainBodyLine` 的过滤语义，别另写一套；
- 每篇笔记最多生成 `min(24, max(8, concepts.size * 2))` 条确定性候选，强的优先，保证几百篇笔记时关系池仍可控；
- 只出现在 frontmatter、正文没出现的概念**不生成共现候选**（没有正文证据），它的关系只能来自显式 `[[…]]`、AI 或用户；
- **`[[…]]` 的「显式」≠「用户手写」**：一期 2026-11-03 起，「本文概念」的唯一来源是正文里的 `[[原文 => 概念名]]` 标注（frontmatter `concepts` 只是派生缓存，删掉进 `removed-concepts` 墓碑，见 `synchronizeConceptMembership`）；但 `markConceptAnnotations` 会把 AI 候选也包成标注，所以现有数据仍分不出「手写标注」还是「AI 打标」。因此 `EXPLICIT` 仍然只是派生候选（比共现强一点），不是用户确认的关系；只有用户在详情里点「确认」后才升级为 `USER` 权威边（§6.7）。
- 派生关系不落盘：每次构建从笔记现算；AI/用户关系分别读两个 json，合并时按硬规则 3 去重、按墓碑过滤。

## 4. 布局：「分层」= 分类深度，不是依赖层

v1.1 里「分层图」的「层」只有一个含义：**分类的深度**。根分类是第 1 层（领域），它的子分类是第 2 层（子领域），概念挂在最末一层下面。用户原话「形式可以类似分类进行划分，那么父节点就是它的所属」就是这个意思。

v1.0 的「依赖层」（L0 地基 → Ln 综合）没有消失，但**不是默认视图**：它降级为可选的「体系视图」，只在用户主动打开且关系足够多时出现（§4.7、§9.3）。这样做的好处：

| 维度 | 依赖分层（v1.0 默认） | 分类树（v1.1 默认） |
|---|---|---|
| 第一次打开能看到结构吗 | 不能：没有前置关系就全在「待连线」 | 能：概念按分类就位，零关系也有树 |
| 关系写得少时 | 图塌成散点 | 树完全不受影响 |
| 边多时 | 糊 | 默认只有归属（靠嵌套表达，不是线） |
| 回答「我有哪些块」 | 靠领域岛（共现聚类，名字是锚点概念，不稳定） | 靠分类名（用户/AI 命名，稳定可改） |
| 回答「这块下面有什么」 | 靠泳道 + 层带 | 靠嵌套层级，一眼看到包含关系 |

### 4.1 画布结构：分区画布（分类框 + 概念叶子）

> **v1.2 已取代**：实际实现是 §4.9 的「森林式树布局」（节点 + 父子连线，没有嵌套框与芯片网格）。本节保留作 v1.1 方案记录。

默认视图不是「节点 + 线」的图，而是**分类分区画布**：分类画成嵌套的圆角框（像文件夹/分区），概念画成框内的叶子芯片。归属靠**嵌套与缩进**表达，树边不画箭头——分类标题到子分类之间最多有一条 1px `dataTrack` 的极淡引导线（帮助视线跟随，不可点、不参与命中、不是关系边）。这是「默认只有最直接的关系」的最彻底做法：视觉噪声最低。

      画布可缩放/平移；根分类按 masonry 流式排布，未分类区排最后
```

- 每个分类一个**框**：标题行 = 折叠箭头 + 分类名 + 计数（`N 个概念 · M 个子分类`；AI 建的加 AI 徽标）；框内先排子分类（递归），再排该分类直接挂的概念芯片；
- 概念芯片：圆角矩形 + 名字（可换行/截断）+ 小徽章（`3 篇`、无定义圆点、只在 frontmatter 虚线框）；不做成实心圆——分类画布是「盒子套盒子」，圆点会像另一种层级；
- 未分类区：一个特殊框「未分类」排在最后，里面是没归属的概念芯片；空时不画；
- 折叠：分类标题行的箭头；折叠后框缩成一行「▸ 名称 · N 个概念 · M 个子分类」，不画内部；
- **默认展开深度 = 2 层**（根 + 一层子分类；更深折叠），概念只在「直接可见的末层分类」里展示；用户点开才展开（展开状态进页内 `KnowledgeGraphViewState`，不落盘）。这样 200 个概念时首屏仍然是一屏可扫的块，而不是 200 行。

### 4.2 确定性分区布局（纯函数）

不用力导向，也不用经典 tidy-tree；用**递归测量 + masonry 打包**，因为分类框是矩形、概念芯片在框内换行，这更接近「分区」而不是「节点图」：

```
layoutKnowledgeGraph(nodes, edges, collapsed, options, warm) -> GraphLayout

# 0. 入参预处理：把节点分成 category 树 + concept 芯片；丢弃非法归属的节点（进未分类）
# 1. 自底向上测量（递归，显式栈）：
#    每个分类框：header 高 30dp；childrenW = 子分类框按 masonry 排布后的宽；
#    概念芯片按「每行可用宽」流式换行：chipW = estimateLabelWidth(name) + padding，
#    每行最多 4 列（窄框）/ 8 列（宽框），行高 30dp，行列间距 8dp；
#    contentW = max(childrenW, chipsW)，contentH = header + childrenH + chipsH + padding；
#    折叠的分类框：contentW = max(160, headerW)，contentH = 30dp。
# 2. 宽度约束：根分类框宽度 = clamp(contentW, 240dp, 720dp)；框内可用宽 = 框宽 - 2*padding；
#    如果子分类框总宽超出可用宽，则子分类框继续向下换行（嵌套 masonry）；
# 3. 根分类按 masonry 打包：按 reading order（sortOrder, name）依次放入当前列，
#    列宽 = max(已放根框宽)，列高累加；放不下当前列就开新列；
#    目标：列数 ≈ ceil(sqrt(总宽积 / 目标高))，由 options.maxCanvasWidth 决定；
# 4. 未分类框作为最后一个根块，放在所有真实根分类之后；
# 5. 坐标分配：根框从左到右、从上到下；嵌套坐标 = 父框内容原点 + padding + 偏移；
# 6. 边路由（只在聚焦时）：见 §4.5，布局阶段只预留 anchor 点；
# 7. bounds = union(所有框) 外扩 32dp；lod = lodFor(...)。
```

**确定性保证**（全部可断言，§10.1）：

- 输入按 `(sortOrder, name, key)` 排序，容器只用 `List`/`sortedMap`，不迭代 `HashMap`；
- 芯片排序：`(noteCount 降序, name, key)`——笔记多的概念在前，符合「重要先看见」；分类排序：`(sortOrder 升序, name, key)`；
- 坐标是纯整数/浮点确定性计算，同输入两次调用**逐位相等**；标签宽度用估算（CJK 1.0em / ASCII 0.55em，误差 ±15%），绘制时用 `TextMeasurer` 实测再截断——估算只影响盒子宽，不影响语义；
- 增量：改了某一个分类的归属，只有它所在的那一列/框重排；`warm` 布局缓存（§7.2 `layout` 段）保存上一版根块顺序与坐标锚点，指纹不变时直接复用，避免每次打开都跳。

**复杂度**：测量 O(N + 分类数)，打包 O(根分类数 × 列数)，坐标 O(N)；2000 概念实测目标 < 30ms（§5.10、§10.1）。不需要 Tarjan、不需要 barycenter、不需要交叉数——这是 v1.1 比 v1.0 简单的地方。

### 4.3 折叠、LOD 与聚合

| 层级 | 判定 | 画什么 |
|---|---|---|
| 展开（正常） | `perNodeArea ≥ 180` 且 zoom ≥ 0.55 | 分类框 + 概念芯片 + 文字标签 |
| 紧凑 | `perNodeArea < 180` 或 0.3 ≤ zoom < 0.55 | 分类框保留，概念芯片只画色块/首字，不画全部标签；超长分类折叠为「名称 · N」 |
| 聚合 | zoom < 0.3 或概念数 > 2000 | 只画根分类块（标题 + `N 概念 / M 子分类`），子分类与芯片不画；点块放大 |
| 超大 | 概念数 > 5000 | 不渲染全图，提示「概念太多，请先搜索或用概念列表」；搜索/列表仍可用 |

- `perNodeArea = 视口面积 × zoom² / 概念数`（沿用 v1.0 审查后的判据，比只看 zoom 更稳）；
- 概念数 > 800 时默认展开深度降为 1（只展开根），并默认隐藏无定义/低提及芯片的标签；
- 折叠不是筛选：折叠的概念仍然参与搜索、统计与「未分类 N」计数；搜索命中折叠内的节点时自动展开祖先（§5.6）；
- 折叠状态是**视图状态**，不落盘（下次打开默认深度 2）；布局缓存只存顺序/坐标锚点，不存折叠。

### 4.4 聚焦叠加：关系只在此刻出现

聚焦 = 选中一个概念节点。画布进入三种同时发生的状态：

1. **淡出**：除选中节点、它的直接关联节点、它们所在分类框的标题外，其余全部降到 18% 不透明度（分类框边框保留 8%，避免失去方位感）；
2. **画关系**：只画与选中节点**直接相连**的边，按 kind 分色（§5.4）；上限 12 条：排序 `USER > AI（有证据）> EXPLICIT > HEURISTIC`，同来源按 confidence 降序；`CO_OCCUR` 默认不画，仅当筛选「显示共现」打开时才加入（最多再 +8 条）；
3. **给邻居打标记**：直接关联的概念芯片加 `accentText` 2dp 描边 + 类型小徽标（`前置`/`应用`/`相关`），分类框标题行加「含关联」小点。

边的路由（聚焦时）：

- 同一分类框内：从两个芯片的相邻边中点画三次贝塞尔（控制点沿水平方向外扩 24dp）；不同框：用正交折线走框间空隙（先水平出框、再垂直、再水平入框），中段在框与框的 gutter 里——避免横穿分类框；
- 目标不在当前可见区域（折叠、屏幕外、聚合态）：不画线，在画布底部弹出**「关联」浮层条**（`在折叠分类中：A（前置）、B（应用）`），点条目 = 展开祖先并定位；最多列 12 条，更多在右栏列表；
- 边本身不可拖拽、不可编辑（G0/G1）；点边 = 高亮两端 + 右栏显示证据；右键菜单在 G2 才做。

聚焦状态清除：点画布空白 / 再点一次选中节点 / `Esc` / 切换到别的视图。**聚焦不改变布局**：节点不移动，避免「点一下全图重排」的眩晕；淡出 + 连线已经足够表达。

### 4.5 稳定性：改一篇笔记，树不要抖

1. **分类不随笔记变**：分类树来自用户/AI 的归属数据，笔记增删只影响概念节点与统计；新概念进未分类区，不会自动插进某个分类（AI 归类除外，且是用户主动触发）；
2. **同一份归属永远同一棵树**：排序、打包、坐标全是确定性的；没有任何随机/时间种子进入布局（时间只用于 id 与缓存失效）；
3. **跨会话**：上一版根块顺序与坐标锚点存 `graph.cache.json` 的 `layout` 段（含 fingerprint：分类树 + 归属 + 概念 key 集的哈希）；指纹没变就 warm 复用（直接复用坐标，不重算）；指纹变了但差异 < 10% 仍 warm（只重排变化的框）；差异大 → cold 一次；
4. **AI 归类后允许一次大重排**：这是用户主动触发的，应用前弹确认（「将把 N 个概念移到 M 个分类，可能重排画布」），确认才写入缓存；未确认的 AI 建议只进「AI 建议」列表，不直接改用户树（G1 可选「自动应用」开关，默认关）。
5. **CJK 标签宽度**是 em 估算（CJK 1.0em / ASCII 0.55em），实测误差约 ±15%，所以芯片宽度留 8dp 余量；**布局用估算宽，绘制用真实测量**，误差只影响芯片留白，不影响坐标稳定性。

### 4.6 画布坐标系与手势

- 世界坐标单位 = dp，绘制时 `screen = world * zoom + pan`；缩放范围 0.25–2.5；
- 画布背景 `surface` + `dataTrack` 点阵（24dp 间距，zoom ≥ 0.8 才画）给空间参照；
- 根分类框之间间距 24dp，列间距 32dp；框内 padding 10dp；芯片间距 8dp；
- 边缘留白 32dp；`fit` 全图时 padding 32dp、zoom 上限 1.5；
- 滚轮以鼠标位置为锚点缩放；拖拽空白平移；触控板捏合若走 `transformable` 同样处理（Desktop 事件差异是已知风险 R7）。

### 4.7 旧的依赖分层：降级为可选「体系视图」（G2）

v1.0 的依赖分层算法**不删**，全部保留为 G2 的可选视图，入口在左栏「视图：分类 / 体系」下拉（仅当关系边 ≥ 8 条时可见）。触发条件与形态：

- 只在用户主动切到「体系」时计算（不再每次打开都算）；默认仍显示分类树；
- 算法与原型验证原样保留（v1.0 的 §4.1–§4.7，此处摘要）：`PREREQUISITE` 硬依据 + `APPLIES` 弱提升 + 硬修复 pass；SCC 环收缩同层；`pins` 锁层 clamp 不整体平移；层内整数 barycenter 4 轮 + 确定性 tie-break；warm/cold 布局缓存；
- 原型（Python 单文件，临时脚本不落仓库）跑过 **26 组 / 48 条断言全 PASS**：确定性逐字节一致、输入乱序无关、增量 ≥90% 层号不变、warm 平均位移 0；2000 节点全链 77ms（Python），Kotlin 预估 2–5ms；示例见 [algorithm-sample.svg](assets/knowledge-graph/algorithm-sample.svg)（32 概念/52 边/5 层带，含 1 个 SCC 环框）与附录 B 的 v1.0 伪代码；
- 为什么降级：用户反馈「链接太乱」+ 大多数笔记没有前置关系；体系视图的价值依赖「关系写得足够多」，放在 G2 作为重度用户功能，不占默认首屏；
- G2 实现时如果发现维护成本高（要维持两套布局），允许**只读的依赖分层图**（不可交互，仅作为分类树之外的参考视图）或直接砍掉——分类树已经满足「快速查看知识体系」的主需求，这一点写进决策记录。

### 4.8 为什么不用力导向

| 维度 | 力导向（d3-force 类） | 本设计（分区布局） |
|---|---|---|
| 同一份数据两次打开 | 节点位置随机/不同 | 完全一致 |
| 可测试性 | 只能测「图没炸」 | 树的框/芯片坐标、排序、折叠都能断言 |
| 语义 | 位置没有含义 | 嵌套=归属，深度=分类层级 |
| 用户改一篇笔记 | 全图重新抖一次 | 分类树不变，只有统计变 |
| 2000 节点 | 物理迭代 + 交叉难控 | 测量+打包线性，LOD 折叠 |
| 链接噪声 | 边越多越乱 | 默认零关系线，只在聚焦时出现 |

### 4.9 v1.2 修订：森林式树布局（取代 4.1–4.3 的「分区画布」）

G0 落地后按反馈简化：画布上只剩节点和父子连线，一棵根分类一棵树。

- **森林**：可见根分类各一棵树，从左到右排；一行超 `maxCanvasWidth`（默认 3000dp）换行。未分类概念合成一个虚拟根「未分类」，永远最后一棵（§3.3 规则 7 的降级区）。
- **节点**：分类 = 虚节点（空心圆角框 + 虚线边），概念 = 实节点（实心圆角框）；节点只显示名字，超宽省略（`estimateLabelWidth + padding` clamp 到 `minNodeWidth..maxNodeWidth`）。绘画布上不再有篇数、提及数、AI 徽标、定义、芯片网格。
- **连线**：父子连线（parent 底边中点 → child 顶边中点，三次贝塞尔），默认**只画这一种**；没有跨树枝、没有关系边（关系边只在聚焦浮窗/聚焦高亮里出现，§5.11）。
- **tidy tree 两遍式**：子树宽 = max(自身宽, 子宽和 + `nodeGapX`)；父节点水平居中于子节点跨度；`y = depth * (max(nodeHeight, categoryHeight) + rowGapY)`；树间 `treeGapX`；同一行内树高取最高一棵。
- **折叠**：`collapsed` 里的分类只画自己、子树剪掉（双击分类切换；`KnowledgeGraphViewState.collapsed` 是纯视图状态，不落盘）。折叠不删除数据，重算即恢复。
- **warm**：`LayoutCache.fingerprint == layoutFingerprint(graph)` 时才复用 `rootOrder`；坐标全部重算（复用旧坐标会在归属变化后叠框）。未分类永远最后。
- **确定性**：所有顺序来自显式排序（分类 `sortOrder→name→key`、概念 `noteCount desc→name→key`），不迭代 HashMap；同输入两次调用逐位相等，单测直接比对。
- **复杂度**：O(N) 测量 + 打包，2000 概念毫秒级；LOD（`lodFor`）保留但只用于极端规模下的提示，不改变树的画法。
- **为什么取代「分区画布」**：嵌套框 + 芯片网格 + 计数徽标在真实截图里显得吵；树本身已经完整表达「谁属于谁」，其它信息交给聚焦浮窗按需展开。

#### 4.9.1 虚节点与拖动链接（v1.3）

- **虚节点入口**：工具条「＋ 虚节点」调用 `addVirtualNode()`（**唯一入口**；左栏只留一句提示，不再放第二个按钮，避免和「新建分类」重复）——生成根分类（名字去重：「新分类」「新分类 2」…）并选中它。虚节点落在顶层，等着被拖到合适的位置；名字随时可在浮窗里改。
- **拖动语义**：只有**分类节点**可拖（概念不可拖，避免误操作把知识点当容器）。从分类按下拖动，拖到某个节点上松手：
  - 落点是**概念** → 该概念 `assignConcept(conceptKey, draggedCategoryId)`（收为该分类的子节点）；
  - 落点是**分类** → 该分类 `moveCategory(targetId, draggedCategoryId)`（连整棵子树一起挂过去）；
  - 落点是空白 → 不链接，虚节点留在原处（不删除，避免误拖丢节点）；
  - 非法落点（自己、自己的后代、自己的祖先）**不高亮**，松手不生效——`canDrop(graph, dragged, target)` 纯函数判定，测试覆盖。
- **手势实现**：不用 `detectDragGestures` 的 `onDragStart` 位置（那是穿过 touch slop 后的点，贴着节点边缘起拖会判不到节点），改成 `awaitEachGesture + awaitFirstDown` 自己写循环：**按下点做命中判定**，再按 `viewConfiguration.touchSlop` 进入拖动；拖动中每帧用指针世界坐标重算落点。空白处拖动仍走相机平移。
- **视觉反馈**：拖动中从被拖节点中心到指针画虚线；合法落点画 accent 高亮框；被拖节点半透明（0.3），松手后恢复。
- **渲染单位（v1.3 补丁，重要不变量）**：画布**世界坐标单位是 px**。布局里的字号/间距必须按屏幕 `density` 放大（`KnowledgeGraphScreen` 用 `LayoutOptions(... × density)`）；否则布局按 12px 算宽、`drawText` 按 12sp 画（Retina 上 24px），中文会被截成一两个字。文字绘制可用宽度直接取节点宽度（只内缩 8px），不要用 `16.dp.toPx()` 与世界单位混减。
- **画布必须 `clipToBounds()`**：节点会随相机平移/缩放画到画布外，不裁剪会盖住左侧栏（v1.3 实测 bug）。
- **图例位置（v1.3 补丁）**：图例是画布右上角的浮层（`KnowledgeGraphLegend`：概念实 / 分类虚 / 父子连线），不再放左栏竖排；左栏只留搜索、统计与 AI 入口。
- **为什么不做「拖拽节点自由排布」**：位置是布局算出来的，拖动只表达「归属」这一种语义；自由排布会破坏确定性布局与跨会话稳定（§4.9 末段）。

│    ├─ tab：笔记 / 概念 / 网络
│    ├─ 网络 tab 默认内容：
│    │    筛选（显示未分类 / 分类默认折叠 / 聚焦时显示关联 / 领域 / 分类深度 1–5）
│    │    → 图例 → 统计卡片（分类 N · 概念 M · 未分类 K · 关联 L）
│    │    → 「补全分类建议」按钮（G1；没配模型时禁用）
│    └─ 输入搜索词时：临时替换为搜索结果分组列表（分类 / 概念 / 笔记），清空后恢复
├─ 主区（Canvas，铺满剩余宽高，不套 1120dp 最大宽）
│    ├─ 左上角浮动：面包屑（`全部 / 检索与生成 / 向量检索`）+ 缩放控件（− / 100% / +）
│    └─ 分区画布（分类框 + 概念芯片，可缩放/平移）
└─ 右栏（320dp，可拖宽 260–420dp，仅网络 tab 有选中节点时出现）
     ├─  concepto 选中 → 概念详情
     └─  分类选中 → 分类详情
```

栏宽、折叠状态、tab 选择都放 `KnowledgeGraphViewState`（页内 object，沿用 `MarkdownSidebarState` 的先例）：切到别的页再回来，视野和选中还在。**这些都不落盘**——不新增配置文件；跨会话的稳定性只靠 `graph.cache.json` 的 layout 段（§7.2）。

> 为什么左栏不做第二棵目录树：**画布本身就是目录树**（分类框可折叠、可点、可 fit），再在左栏放一棵列表树是重复投影，窄窗口下还会挤压画布。左栏只放「筛选 + 图例 + 统计 + AI 入口」四件事；找具体分类靠画布折叠/面包屑/搜索。

### 5.2 网络视图的左栏

- **搜索框**：跨「分类名 / 概念名 / 笔记标题」过滤；输入时左栏临时切成搜索结果分组列表（分类 / 概念 / 笔记），点结果 = 选中 + 定位（§5.6）；清空搜索恢复筛选面板；
- **筛选**：
  - `显示未分类`（开关，默认开）：关掉后画布不画未分类区，统计仍显示 `未分类 N`；
  - `分类默认折叠`（开关，默认关）：打开后除根分类外全部折叠，一屏看全领域；
  - `聚焦时显示关联`（开关，默认开）：关掉后聚焦只淡出、不画关系线（右栏列表仍在）；
  - `领域`（下拉，默认「全部领域」）：只显示某个根分类及其子树，其余隐藏（不是删除）；用于专注一个领域；
  - `分类深度`（1–5 分段控件，默认 2）：控制默认展开深度；调大 = 多看一层，调小 = 更聚合；
- **图例**：四种关系边 + 分类框/概念芯片/AI 徽标/未分类区的样式说明；默认展开，可收起（收起后只留「?」小钮）；
- **统计卡片**：`分类 N · 概念 M · 未分类 K · 关联 L`（关联 = 合并后的关系边总数，默认不画；点「未分类」= fit 未分类区；点「关联」= 说明浮层「关联只在聚焦时显示」）；
- **「补全分类建议」按钮**（G1）：手动触发的全图 AI 归类（§6.2）；没配模型时禁用并提示「先在设置里配置模型」；按钮下方小字写明「AI 只生成建议，确认后才写入分类树，每次手动触发，有成本」；
- **新建分类**：入口不在左栏（避免和筛选挤），在画布顶部工具条与未分类区的 `+ 新建分类` 按钮、右栏分类详情里（§5.3/§5.8）。

> 左栏不做第二棵目录树：画布就是树，分类的展开/折叠/选中都在画布上完成；左栏负责「过滤视野、看统计、叫 AI」，窄窗口下还能收成 36dp。

### 5.3 画布与顶部浮动条

- 画布左上角：**面包屑**（当前选中分类的路径；无选中时显示「全部」）+ **缩放控件**（`− / 100% / +`，点百分比回到 100%）；
- 画布顶部工具条：`+ 新建分类` / `分类树`（默认选中；G2 后旁边出现「体系视图」）/ `展开全部` / `折叠全部` / `适应窗口` / `导出图片`（G2）；
- 画布右下角：**图例浮层**（默认折叠成「?」小圆钮，展开显示分类框/概念芯片/AI 徽标/四种边样式）；
- 画布顶部的 AI 建议条（G1）：`AI 建议 3 条归类 · 查看`（点开 = 右栏 AI 建议列表）；静默、不打断。

### 5.6 搜索与定位

网络视图的搜索是**两级**的：

1. 左栏搜索框：实时过滤「分类名 / 概念名 / 笔记标题」，左栏临时换成结果分组列表（分类 / 概念 / 笔记），点结果 = 选中 + 定位；清空后恢复筛选面板；
2. 概念定位：命中概念 → 沿 `parentKey` 展开所有祖先 → 把画布平移/缩放到该芯片居中（目标 zoom ≥ 0.8）→ 选中并聚焦；
3. 「在笔记中定位」：**先看片段、再跳原文**——点概念后右栏「来源」列表先列出标注过该概念的笔记（一期 `ConceptDetail.mentions` 已带 `noteId/snippet/start/end`，按笔记更新时间降序；一期详情已分「标注过的笔记 / 其他提到」两组，网络视图沿用），每条 1–2 行片段；点某条才走一期定位链路（`locateMention` 设 `pendingReveal(noteId,start,end)` → 切到笔记 tab → `revealToken` 递增 → 编辑器选中并滚动）。**不内嵌整篇预览**：一期的笔记页已没有「预览态」（编辑预览一体化，页头只剩目录/导出/菜单），为图视图再搭一套只读渲染/滚动会把编辑器分叉；图里定位的语义是「回到源头」，完整上下文在笔记页（见 Q2）；
4. 搜索命中折叠分类内的概念时自动展开路径；命中但所在分类不合法（被丢弃）时提示「该概念的分类归属无效，已放入未分类」。

### 5.7 概念详情（右栏）

| 区块 | 内容 | 操作 |
|---|---|---|
| 头部 | 名字（可换行）+ 徽标（AI / frontmatterOnly / 无定义） | — |
| 所属 | 分类路径面包屑（`检索与生成 / 向量检索`），未分类显示「未分类」 | 「移动到分类…」（选分类树，G0）/「新建子分类」（G0） |
| 定义 | `concepts.json` 的定义，空时显示「还没有定义，写一句？」 | 点进输入框编辑（写回同一个 `concepts.json`；已有一期 `ConceptMetaStore.saveDefinition`） |
| 统计 | `N 篇笔记 · M 次提及 · 最近更新 11-02` | — |
| 来源（先预览） | 标注过该概念的笔记列表（一期 `ConceptDetail.mentions`，按笔记更新时间降序；每条 = 笔记标题 + 命中整行片段，长行按一期 `snippetAround` 截断；「其他提到」折叠在下面） | 点条目 = 跳转并选中命中片段（复用一期 `locateMention`/`pendingReveal`）；不内嵌整篇预览（Q2） |

概念详情是**导航器**：所有区块的目标都是「点一下回到原文」或「看一眼它属于哪」。不显示掌握度、正确率、复习状态（§2.2）。

### 5.8 分类详情（右栏）

| 区块 | 内容 | 操作 |

| 统计 | `N 个概念 · M 个子分类 · 最近更新` | — |

### 5.9 空态与降级

| 情况 | 显示 |
|---|---|
| 一篇笔记都没有 | 画布中央空态：「还没有笔记。先写一篇，概念会在这里长出来。」+「新建笔记」 |
| 有笔记但没有概念 | 「笔记里还没有登记概念。编辑笔记时让 AI 整理一次，或手动点亮概念。」+「去整理」 |
| 有概念、没有分类 | 只画「未分类」区 + 引导横幅：「让 AI 帮你先分个类，或手动新建分类」；无 LLM 时横幅只说「手动新建分类」 |
| 分类归属不合法（环/超深/父不存在） | 画布顶部黄条：「有 N 条分类归属无效，已放入未分类」+「查看详情」（列出 concept/category 与原因）；不阻塞渲染 |
| LLM 未配置 | AI 按钮禁用，hover 提示「先在设置里配置模型」；手动新建分类/移动/关系照常可用；不弹报错（一期已有「AI 没配置」的提示口径） |
| 概念 > 2000 / > 5000 | §4.3 的聚合/提示；不假装能画 |
| 关系为空（聚焦时） | 右栏「直接关联」显示「还没有关系。AI 整理时会顺手抽同篇概念间的关系（G1），也可以手动加（G2）」 |

### 5.10 性能与可访问性

- **单个 Canvas** 画整张图：不做「每个节点一个 Composable」（几百个 Composable 会拖垮重组）；缩放/平移状态只在 draw lambda 里读，避免触发重组；
- 分层绘制：分类框背景 → 芯片底 → 文本 → 边（聚焦时）→ 选中/邻居高亮 → 浮层；`drawWithCache` 缓存不随 pan 变化的 Path；
- 视口裁剪：只画与视口相交的框；芯片数 > 800 时只画视口内 + 1 屏缓冲区；
- 标签：先 `TextMeasurer.measure`（G0 第一件事的 spike，见 §9.1）拿真实宽度，再截断（`…`）；截断字符串 + 宽度一起缓存，避免每帧测量；
- 目标：打开网络 tab 首帧 < 200ms（200 概念、3 层），缩放/平移 < 30ms/帧；LOD 保证极端数据不卡；
- 可访问性：所有点击目标用 Canvas 命中测试但保留等价键盘路径（左栏树、搜索、右栏按钮都是真 Composable，可 Tab 到）；对比度按 token 保证（`data`/`accentText` 与浅色背景、暗色主题分别验证）；字号跟随全局 fontScale；聚焦/选中不只用颜色（描边 + 徽标）；不做自动动画（无 `animate*` 环绕画布），避免眩晕。

### 5.11 v1.2 修订：聚焦浮窗（取代 5.7 / 5.8 的右栏详情）

  - 「新建上级分类」＝先建一个根分类，再把当前分类挂进去——这是把「检索 / 生成 / 评估」收进一个新大类最顺手的入口；
  - 「移动到分类…」列出「顶层（成为根分类）」+ 其它分类，**排除自己与自己的后代**（单父、不成环），移动后整棵子树跟着走。

- **位置**：节点右上角 +14dp；右边放不下翻到左侧；纵向夹在视口内；宽 300dp、最高 420dp、内部滚动。浮窗是画布的覆盖层（不占布局宽度），画布仍铺满。

## 6. 分类与关系的来源：AI 只建议，用户是编辑

v1.1 里 AI 做两件事：**给概念找个所属分类**（新）和**给聚焦时看的关系补候选**（沿用）。两件事都遵守同一条底线：**AI 从不直接改 `graph.user.json`**；它的产出全部进 `graph.cache.json`，由用户在右栏逐条或整批确认后才转正。

| 来源 | 谁产生 | 写哪 | 时机 | 成本 |
|---|---|---|---|---|
| A 用户 | 用户新建分类、移动概念、确认建议、合并/删除、加/删关系（G2） | `graph.user.json` | 随时 | 0 |
| B 笔记派生 | 确定性规则：同段/相邻共现、显式 `[[…]]`（§3.5） | 不落盘 | 每次构建现算 | 0 |
| C 笔记内 AI | 现有「整理笔记」那次调用**顺便**输出归类建议 + 同篇关系 | `graph.cache.json` 的 `noteSuggestions` | 编辑器失焦、正文真变了（一期已有） | **零额外调用** |
| D 全图 AI 归类 | 用户点「整理分类」后分批归类未分类概念 | `graph.cache.json` 的 `globalCategories` | 手动触发 | 每批 1 次调用 |

### 6.1 笔记内整理（搭现有整理的车）

一期 `organizeNote`（`KnowledgeScreen.kt:222`）在编辑器失焦时调一次 `KnowledgeExtraction.buildKnowledgeExtractionMessages`，正文最多 6000 字，输出 `{concepts, fills}`。二期**同一次调用**多要两个字段，不新增请求：

```json
{
  "concepts": [{"name": "向量检索", "definition": "把文本编码成向量后按相似度找片段。"}],
  "fills":    [{"label": "标签", "text": "RAG"}],
  "categories": [
    {"name": "向量检索", "categoryPath": ["检索与生成", "向量检索"], "reason": "正文在讲召回与相似度"}
  ],
  "relations": [
    {"from": "向量检索", "to": "RAG", "kind": "PREREQUISITE", "reason": "先有召回再谈增强生成",
     "evidence": "RAG 的第一步是用向量检索拿到候选片段"}
  ]
}
```

提示词新增要求（全部写进 `buildKnowledgeExtractionMessages` 的 user 段）：

- `categories`：只对你本次抽出的概念（以及正文里已有的概念）给建议；`categoryPath` 最多 2 层，每层 ≤12 字；分类名要像「领域/子领域」而不是句子；不确定就不给（宁缺毋滥，别为了交差硬编）；
- `relations`：只在**都在本篇正文出现过**的概念之间给；`kind` 只能是 `PREREQUISITE`（from 是前置）/`APPLIES`（from 是被应用的基础）/`RELATED`；方向要明确；一篇最多 6 条；`evidence` 必须是正文里逐字出现的句子（≤60 字），`reason` ≤40 字；没有就返回空数组；
- **不要让 AI 猜现有分类树**：prompt 不带分类树（避免 6000 字正文被挤掉），它给的 path 只是「建议路径」；合并时如果某个现存分类同名/同路径就直接用，否则创建一个 AI 分类（origin=AI, confirmed=false）；
- 输出仍要求严格 JSON；老的 `{concepts, fills}` 形状必须继续被容忍（解析失败时退回一期行为，不阻塞保存）。

**校验（客户端，纯函数 `KnowledgeGraphAi.kt`）**：

1. `categories[].name` 必须逐字出现在正文；`categoryPath` 每层 normalize 后非空、≤12 字、≤2 层；概念必须在概念的并集里；
2. `relations` 的 from/to 都必须在**本篇概念集**里（不能凭空造概念）；`evidence` 必须 `body.contains(evidence)`（真子串，忽略前后空白）；不满足整条丢弃并计数；
3. 按 `(from,to,kind)` 去重；confidence 按 kind 固定（PREREQUISITE 0.7 / APPLIES 0.6 / RELATED 0.5），不让模型自己报confidence；
4. 已属于某个分类的概念，不再收 AI 的**新增**归类建议（用户先归的算数）；已有人工关系挡住 AI 同向关系；
5. 全部通过后写缓存：`noteSuggestions[noteId] = {bodyHash, categories, relations, createdAt}`。**写入缓存不代表生效**：默认视图照旧显示用户树；AI 建议在左栏「AI 建议（N）」和概念详情里可见，用户确认后才进 `graph.user.json`。

**v1.3 口径（重要）**：AI 整理不再只输出「路径字符串」，而是**图操作**——`createCategory(name, parent)`、`renameCategory`、`link(node, parent)`（概念=归属、分类=移动）。上面的 `categoryPath` 只是同一操作的紧凑表达；确认时按路径逐层建/复用分类再链接，和用户手动「＋ 虚节点 → 拖动 → 改名」执行的是同一套 `KnowledgeGraphTaxonomy` 纯函数。这样 AI 与手动没有两条代码路径，AI 只是把人的三次操作合成一次建议。

### 6.2 全图整理（手动触发）

入口：网络 tab 页头 `整理分类`（或左栏 AI 建议卡片的「AI 帮我归类」）。前置条件：模型已配置；没有未分类概念且没有未确认建议时按钮禁用并提示「没有需要整理的概念」。

流程：

```
1. 点「整理分类」→ 确认弹窗：
   「将把 37 个未分类概念分成 1 批（每批 ≤40）发给模型；预计 1 次调用，约 N 秒。
     这只生成建议，不会自动改你的分类。继续？」
2. 分批（顺序、可取消）：
   每批请求 = 未分类概念的 key/name/definition（definition 截 40 字）
               + 现有分类路径（最多 60 条，只取前 2 层）
   每批要求：给每个概念一个 categoryPath（现有路径或新路径）+ reason ≤40 字，严格 JSON。
3. 合并：
   路径按名字（忽略大小写/空白）映射到现有分类；没有则创建缺失分类（cache 里先记 id=临时 key；
   用户确认时才在 user.json 里真正创建，避免污染用户树）;
   产出 categorySuggestions: {conceptKey → {categoryPath, reason, batch}}
4. 写 graph.cache.json（含 conceptSetHash + promptVersion + model，供失效判断）；
5. 左栏「AI 建议（N）」+ 画布顶部提示条出现；用户可「全部确认 / 逐条确认 / 全部忽略」。
```

批量与边界：

- 每批 ≤40 个概念；一次运行最多 20 批（800 个概念），超过提示「先手动分一部分，再整理剩下的」；
- 批间串行（不并发打模型）；用户取消 = 停止后续批次，已完成批次保留；
- 单批失败（非 2xx/JSON 解析失败/名字对不上）：跳过该批、记录失败数，最后提示「N 个概念没整理成功」；不重试（重试由用户再点一次），不静默重跑；
- 已确认/已忽略的建议不重复发（墓碑过滤，§6.7）；缓存 `conceptSetHash` 没变时不重新请求，直接显示「已是最新（缓存）」；
- **绝不自动应用**：没有「自动归类」开关；确认弹窗的文案必须写清「只生成建议」。

### 6.3 确认、改名、移动、合并：写完即所见

- **确认**：`graph.user.json` 里创建缺失分类（origin 取自缓存里 AI 的路径，confirmed=true）、写 `assignments[conceptKey]=categoryId`、从缓存建议里移除；`updatedAt` 更新时间；
- **改名**：只改分类节点的 `name`，id 不变，所有归属自动跟随；
- **移动概念**：下拉选分类树 → 写 `assignments`；如果该分类折叠着，展开目标分类并高亮概念（一次本地重排，§4.5）；
- **合并分类**：A → B，写 `mergedInto[A]=B`、把 A 的子分类/概念改挂 B、写 `removedCategories` 墓碑（记录 A 的路径）；下次渲染沿 `mergedInto` 解析旧 id；
- **删除分类**：确认弹窗列出影响数 → 子分类上移父级、概念回未分类、写墓碑；
- 所有写操作走同一个 `KnowledgeGraphStore.saveUser()`（原子写 + `.bak`），失败时 UI 提示「没写进去」并保留界面状态，不悄悄丢改动。

### 6.4 AI 关系建议

- **笔记内（C，G1）**：上面 `relations` 字段，随「整理笔记」免费产出；evidence 可点回原文；在概念详情「AI 建议」里逐条确认（或整批「全部确认」）；确认后 source=AI 的关系写 `graph.user.json` 的 `relations`（用户认可后就算用户数据，不再依赖缓存）；
- **全图（D2，G2 可选）**：聚焦用关系不要求覆盖全图；如果以后用户抱怨「同一个概念在不同分类里关联不到」，再做事后补全：按分类/领域分批（每批 ≤40 概念）让 AI 给前置/应用关系，无 evidence，confidence 0.4–0.6，显示为「AI 推测」虚线；默认不显示，筛选项里开；
- **原则**：关系只是聚焦时的辅助阅读，**不追求覆盖率**；宁可没有，不可乱连。这是对用户「链接太乱」反馈最直接的回应——默认画布一条关系线都没有。

### 6.5 提示词与解析的工程约束

- 复用一期的 `parseExtractionResult` 外层（取第一个 `{` 到最后一个 `}`，容忍代码围栏/寒暄），内部多解析 `categories`/`relations`；解析失败 = 空建议 + 原有 concepts/fills 照常应用；
- `LlmClient.complete` 已强制 `jsonMode=true`；`HttpLlmClient` 默认 temperature 0.2、maxTokens 2048、timeout 90s（沿用，不加 per-call 参数——大图抽取靠分批解决）；
- 模型返回里未知字段忽略；`categoryPath` 也容忍字符串（`"A / B"` 会被 split 成两层）；
- **提示词与解析器必须匹配**：新增字段的提示词文本、解析器、mock e2e、`PromptCatalogTest`/`KnowledgeConceptTest` 一起改（铁律 §7.9）。

### 6.6 成本与隐私

- 笔记内整理：**0 次额外调用**（搭车）；
- 全图整理：每 40 个未分类概念 1 次调用；按 1000 概念、800 个未分类估算 ≈ 20 次调用。确认弹窗显示「预计 N 次调用」，不写死钱；缓存命中时 0 次；
- 失败重试：每批最多 1 次由用户手动「重试失败批次」，不自动重试；
- 隐私：发出去的是「概念名 + 定义 ≤40 字 + 分类路径」，**不发笔记正文**（全图整理）；笔记内整理本来就发正文（一期既有行为，同一个信任边界）。不接活动数据（一期 `ActivitySettings.aiExposure/titleRedactions` 只有声明没有实现，喂 AI 前必须先把裁剪做完，这不是本期范围）。

### 6.7 墓碑：删掉的东西不要被 AI 复活

| 墓碑 | 键 | 什么时候写 | 效果 |
|---|---|---|---|
| `removedRelations` | `(fromKey, toKey, kind)` | 用户删掉一条 AI/用户关系 | 所有来源（含派生）都不再显示这条边 |
| `removedAssignments` | `(conceptKey, categoryPath)` | 用户忽略某条 AI 归类建议 / 把概念从分类拖回未分类 | AI 不再建议同一组合；概念留在未分类 |
| `removedCategories` | `(categoryId, path, at)` | 删除或合并分类 | 全图整理时不会原样重建同名分类；`mergedInto` 负责旧 id 解析 |
| `ignoredSuggestions` | `(conceptKey, 建议指纹)`（G1） | 用户点「忽略」 | 建议从缓存里移除且不再出现 |

墓碑都在 `graph.user.json` 里（用户数据，权威）。**可恢复**：G1 右栏「AI 建议」底部提供「已忽略的建议」列表，可恢复单条（清墓碑 + 保留缓存中的建议）；G0 不做恢复 UI，但文件格式预留。墓碑不是黑名单：它只挡 AI 建议，不挡用户手动操作（用户想再建同名分类/再加同一条关系，随时可以）。

### 6.8 计划接入（G2 预留，不在本期做）

- `occurrence.completed` 事件 payload 已带 `unitId`（integration 调研确认），知识侧只需消费事件，不必先改计划库；
- 若要做「学习过」标记，新增 `unit_concept` 表（幂等 DDL，旧库自动建表）或用笔记 frontmatter extras（`unit:`），但 **unit id 跨计划版本会变**，关联要用业务键或随版本复制；
- 语义红线不变：**执行过 ≠ 记过**。计划完成只给节点加一个「学习过」的外圈环，不点亮、不改分类、不产生关系；节点仍必须由笔记/用户创建；
- 预留 `GraphNode` 的 `kind` 与状态叠加入口（不改节点语义）；第 3 条「能力地图」将来的节点类型用独立 `nodeKind` 扩展，不塞进 CATEGORY。

## 7. 存储

### 7.1 四个文件

| 文件 | 内容 | 谁写 | 丢了会怎样 |
|---|---|---|---|
| `knowledge/notes/<id>.md` | 笔记正文 + frontmatter `title/created/updated/concepts` | 一期编辑器 | 真相丢失，**备份优先** |
| `knowledge/concepts.json` | 概念定义 `{name, definition}` | 用户 + AI 只填空 | AI 会重新问定义，不阻塞 |
| `knowledge/graph.user.json` | 分类树、归属、用户关系、墓碑、排序 | 用户（UI） | 分类树与策展丢失；概念回未分类；**graph.cache.json 里的 AI 建议不会自动转正** |
| `knowledge/graph.cache.json` | AI 建议（笔记内归类/关系、全图归类、全图关系）+ 布局缓存 | AI 流程 | 下次重新整理；布局重排一次；**不影响用户树** |

不新增 `knowledge.db`，不建索引库——一期的「删库重建一致」原则继续成立：删掉两个 graph json，图会退化成「全未分类 + 只有派生关系」，但不会错、不会崩。

- 原子写 + 多实例：两个窗口同时改仍是「后写覆盖先写」（风险 R10，与一期 store.json 一致），不引入锁。

### 7.4 重算与失效

| 变化 | 失效范围 | 怎么算 |
|---|---|---|
| 笔记正文变了 | 该篇 `noteSuggestions` | `bodyHash = fnv1a64(title + "\n" + body)`；比对缓存里的值 |
| 笔记 frontmatter `concepts:` 变了 | 全图概念集、分类建议、布局 | `conceptSetHash = fnv1a64(排序后的 conceptKey 列表 + 分类树结构)` |
| 分类树/归属/改名变了 | 布局缓存（`layout.fingerprint`） | 分类 id+parentId+order 列表 + assignments 的 `conceptKey→categoryId` 列表 + concept key 集 |
| 用户确认/忽略建议 | 对应缓存条目 + 墓碑 | 确认 = 从缓存删并写 user.json；忽略 = 写墓碑并从缓存删 |
| 模型/提示词版本变了 | 全部 AI 建议 | `promptVersion` / `model` 不一致 → 忽略缓存，提示「模型或提示词变了，建议已过期」 |

布局的「差异 < 10% 仍 warm」：差异度 = `(变更的节点键数 + 变更的边归属数) / (节点数 + 归属数)`；任何 `categories/assignments/removed` 的增删算 1 项，改名/改 order 算 0 项（不影响位置）。差异 ≥10% 才 cold 重排；AI 归类确认后允许一次大重排（§4.5）。

### 7.5 时间与 id

- 所有时间戳经 `runtime.clock`（`TrellisClock.nowMs()`）；**禁止 `System.currentTimeMillis()` / `Instant.now()` 取业务时间**（铁律 §7.4）；笔记的 created/updated 用 frontmatter 里的值（一期已解析）；
- 分类 id：`c_` + 8 位十六进制，由 store 在创建时用「时钟毫秒的哈希 + 自增计数器」生成，冲突重试 ≤100（一期 note id 同款做法）；**改名不换 id**；
- AI 建议的 `createdAt` 也走 clock；显示时间用 `knowledgeTimeLabel`（一期，zone 已处理）。

### 7.6 与一期数据的兼容

- 一期没有 graph 文件 → 首次打开网络 tab 是「全部未分类」的状态，不是错误；不自动创建任何文件，直到用户/AI 真的产生分类或建议（读取时文件不存在 = 空对象）；
- 一期 `concepts.json` 不动：定义仍在那里，图的节点读它；不要在 graph.user.json 里复制定义；
- 一期笔记 frontmatter 不加新字段（本期不写笔记）；如果将来要记录「笔记级归类提示」，放 extras（一期已保留未知 key），但仍以 graph 文件为准。

### 7.7 读写实现约定

- 用 `kotlinx.serialization.json` 的 `JsonObject`/`buildJsonObject` 手工读写（app/desktop 有运行库，但**没有 serialization 编译器插件**，不要写 `@Serializable`——`ConceptMetaStore` 已经是这个范式）；
- 文件名常量放 `KnowledgeGraphStore` 的 companion；路径 `File(home, "knowledge/graph.user.json")`；
- 读写函数都 `internal`、纯同步（文件小，几十 KB）；UI 侧在 `LaunchedEffect` 里调，不阻塞首帧；
- 写前 `.bak`；写用临时文件；读先去 BOM；解析异常捕获后返回 null + 留档（不用 `runCatching` 包插件调用——这里不是插件，但保持同样的显式 `try/catch` 风格）。

### 8.4 一次打开网络 tab 的数据流

1. `KnowledgeGraphStore.loadUser()` + `loadCache()`（都在毫秒级，读两个小 json）；
2. `KnowledgeStore.allNotes()` + `conceptIndex()` + `ConceptMetaStore.load()`（一期已有，无新增文件 IO 之外的成本）；
3. `buildKnowledgeGraph(...)`：派生节点 → 建树 → 派生关系候选 → 合并 AI/用户关系 → 墓碑过滤 → 校验 → 统计/诊断；
4. `layoutKnowledgeGraph(graph, collapsed, warm = cache.layout)`：指纹命中则 warm；
5. Canvas 绘制；整个过程不写任何文件（除非用户/AI 产生变更）；这就是 [data-flow.svg](assets/knowledge-graph/data-flow.svg) 的阶段 1–6。

### 8.5 为什么放在 app/desktop，而不是先建模块

- 一期知识库本身就在 `app/desktop`（`KnowledgeStore`/`KnowledgeScreen` 等），图直接复用这些类；先建 `:features:knowledge` 会把「改一版图」变成「跨模块重构」；
- 契约稳定后可平移到 `sdk-domain/.../knowledge/` + `:features:knowledge`（一期 draft §9 已把拆模块列为 P1 重构项）；前置条件是 DTO 稳定、图逻辑被计划/AI 复用；
- 本设计**不碰内核**：图完全在宿主页面内，宿主自己画，不进 `UiNode` 词汇表——与一期 draft §5 的边界结论一致（只是把「局部图」升级成了「宿主自绘的全图」，仍在宿主侧）。

### 10.4 手动验收清单

**G0**：新建分类 → 改名 → 建子分类 → 移动概念 → 删除子分类（子分类上移）→ 合并两个分类 → 重启应用确认树原样 → 聚焦概念看关系 → 点「在笔记中定位」→ 跳笔记并选中命中片段 → 折叠/展开/缩放/平移/fit → 深色主题 + fontScale 1.25 下标签不重叠。

## 11. 风险、取舍与待拍板

### 11.1 风险

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | AI 分类质量差（乱分/造碎分类） | 树不可信 | 只建议不直接应用；确认门；AI 徽标；合并/删除；未分类兜底 |
| R2 | 单父分类表达不了一些概念（既是 A 也是 B） | 用户觉得别扭 | 明确非目标；用分类描述/关系表达；G2 再评估多重归属 |
| R3 | AI 造分类膨胀（每批建一堆新父） | 树越来越深越碎 | 同路径同名去重；深度上限 5；分类名 ≤12 字；合并入口；全图批次确认 |
| R4 | 聚焦关系仍多（用户嫌乱） | 回到 v1.0 问题 | 上限 12、按来源排序、共现默认隐藏、右栏列表兜底 |
| R5 | 布局漂移/跳（改一篇笔记树就动） | 眩晕 | 分类树不随笔记变；确定性；warm 指纹；差异阈值 |
| R6 | **Compose Desktop 文字绘制无先例**（`rememberTextMeasurer`/`drawText` 未编译验证） | 画不出中文标签 | G0-0 30 分钟 spike；备选：`drawIntoCanvas` + `nativeCanvas.drawString`（Skia）或 `Text` composable 定位（性能差、不在节点外层用） |
| R7 | 触控板滚轮/捏合事件差异 | 缩放不灵 | Desktop `onPointerEvent(PointerEventType.Scroll)` + `transformable`；不灵就先只支持滚轮；G1 补 |
| R8 | 800+/2000+ 概念性能 | 卡顿 | 单 Canvas + 视口裁剪 + LOD；性能测试；超 5000 不渲染全图 |
| R9 | 一个分类下概念极多（宽/高爆炸） | 一块巨大 | 芯片流式换行 + 折叠 + 分页（>200 折叠）；G2 可加「更多」 |
| R10 | 多实例同时写 `graph.user.json` | 后写覆盖 | 与一期 `store.json` 同款限制；不引入锁；文档写明 |
| R11 | 两个概念其实是同一个（`RAG`/`检索增强生成`） | 树里更明显 | 一期 2026-11-03 已支持别名匹配/高亮/检索（`ConceptIdentity.aliases`）；G2 补「把两个已存在概念合并」入口（迁移归属/关系/标注），不做自动合并 |
| R12 | AI 调用成本/失败 | 用户不满 | 手动触发 + 批量上限 + 确认成本 + 缓存 + 可取消；失败跳过不重试 |
| R13 | 删掉的关系/分类被 AI 复活 | 白删 | 墓碑（§6.7）；过滤所有来源 |
| R14 | 用户分类丢失（坏文件/误操作） | 策展丢失 | `.bak` + `.bad-*`；删除/合并确认；G1 从 `.bak` 恢复 |
| R15 | 依赖体系视图维护成本（两套布局） | 长期负担 | G2 可选、可只读、可砍（§4.7/§9.3） |
| R16 | 中文排序用 Unicode 码点（不是拼音） | 排序不符合直觉 | 确定性优先；文档写明；G2 可加拼音排序但会破坏「同输入同输出」的可复现性，需谨慎 |
| R17 | 聚焦关系的 evidence 在笔记改动后失效 | 点证据跳错位置 | 关系在构建时现算（派生）或 bodyHash 失效缓存（AI）；跳转用当前正文重新匹配概念名兜底 |

### 11.2 已拍板的取舍

1. **默认是分类树，不是依赖图**（用户 2026-11-02 反馈；依赖视图降 G2）；
2. **默认零关系线**：关系只在聚焦时出现（同反馈）；
3. **单父**：不做多父/多重继承；用分类路径+关系表达交叉；
4. **AI 只建议、不自动应用**；确认后才写用户文件；
5. **宿主 Canvas 自绘**，不进插件词汇表、不新增挂载点；
6. **两个 json**：用户策展 vs AI 缓存物理分开，AI 永远不写用户文件；
7. **确定性布局**，不用力导向；同输入同输出、可 warm；
8. **G0 先手动、无 AI**：没配模型的用户也能完整用「看见 + 归类」；
9. **不碰内核/计划/活动/AI 工具**：本期只在知识页内闭环；
10. **分类树由用户/AI 创建，概念必须来自笔记**：不从计划/活动凭空造概念。

## 附录 B：布局伪代码

### B.1 分区布局（v1.1 默认）

```
layoutKnowledgeGraph(graph, collapsed, warm, options):
  roots = graph.childrenOf[null].filter(CATEGORY)          # 已排序
  rootBoxes = roots.map { measureBox(it) }                 # 自底向上递归
  for box in rootBoxes:
      if box.key in collapsed: box.size = (max(160, headerW), 30)
      else:
          children = graph.childrenOf[box.key]             # 子分类
          childBoxes = children.map { measureBox(it) }     # 递归
          chips = children.filter(CONCEPT)                 # 直接概念叶子
          contentW = max(packWidth(childBoxes), packWidth(chips))
          contentH = headerH + packHeight(childBoxes) + chipsHeight + 2*padding
          box.size = (clamp(contentW + 2*padding, 240, 720), contentH)
  if warm != null && warm.fingerprint == layoutFingerprint(graph):
      restore rootOrder/anchors from warm                     # 直接复用坐标
  columns = packRootBoxes(rootBoxes, options.maxCanvasWidth)  # masonry，确定性
  assignCoordinates(columns, roots, recursive=true)           # 分数像素，四舍五入到 0.5dp
  bounds = union(all boxes).expand(32)
  return GraphLayout(bounds, boxes, chips, byKey, stats, fingerprint)

# 注意：输入先按 (sortOrder, name, key) 排序；不使用 HashMap 迭代顺序；
#      chip 排序 (noteCount desc, name, key)；所有浮点计算在任何平台一致。
```

### B.2 依赖分层（v1.0 备选，G2「体系视图」）

```
assignLayers(nodes, edges, pins) ->
  1. 过滤 confidence < 0.35；PREREQUISITE 硬边、APPLIES 弱边
  2. Tarjan SCC（显式栈）→ 凝缩成 DAG；环内节点同层
  3. 最长路径分层（PREREQUISITE）：h(v) = 1 + max(h(pred))
  4. APPLIES 弱提升：h(v) = max(h(v), h(u)+1)（u 是 APPLIES 的 from 基础侧）
  5. 硬修复 pass：任何 PREREQUISITE 边 from→to 必须 h(from) < h(to)，
     若违反则 to = h(from)+1（递归上推）
  6. pins：锁定层号 clamp 到 [0, maxLayer]，不整体平移；冲突写诊断
  7. 只有 APPLIES 没有 PREREQUISITE 的图：单遍最长路兜底 + 标注「估算」
  8. 层内排序：整数 barycenter（BC_SCALE=1024）4 轮（自下 2 + 自上 2），
     排序键 (barycenter, 上一版 order, firstSeenAt, key)
  9. warm/cold：交叉数增长 >50% 触发 cold；否则沿用上一版顺序；
 10. 坐标：泳道×层带，节点宽 = estimateLabelWidth + 24，高 28/34/40（mentionCount 三档）
```

原型已验证 26 组 / 48 条断言（确定性、乱序无关、增量稳定、warm 位移 0、2000 节点 Python 77ms / Kotlin 预估 2–5ms）；实现时要求显式栈 Tarjan、`IntArray`/`FloatArray`、不迭代 `HashMap`（见 v1.0 §4.7 与 `algorithm-sample.svg`）。
