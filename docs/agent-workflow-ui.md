# Agent 工作流清单：设计说明

> 目标：agent 定好步骤后，用户**先看见清单和进度**，再看结果。
> 对应代码：`app/desktop/.../ChatState.kt`（数据）、`WorkflowTools.kt`（工具）、`AppRuntime`（状态机）、`PlanPanel.kt`（右栏 + 常驻条）、`ChatScreen.PlanThreadLink`（线程入口）。

## 0. 版本说明

| 版本 | 位置 | 结论 |
|---|---|---|
| v1 | 内联卡片，紧跟用户那句话 | 能看懂，但**越滚越远**：长轮次里清单被推出屏幕，用户想知道「现在到哪了」要往回翻 |
| **v2（当前）** | **右侧常驻栏**；关掉后贴在输入框上方 | 常驻、不随滚动跑掉、随时能控制；线程里只留一行入口 |

v2 的触发原因是评审文档 `trellis-review/工作流清单.md`：位置首选右侧常驻栏（296px），内联卡只适合复盘。v1 的问题在于把「过程」和「历史」挤在同一处：清单既要在场、又是历史，滚动是必然冲突的。

## 1. 要解决的问题

会话页原来只有两种信息：结论（大字）和过程（可折叠的一行调用日志）。两者都不回答一个问题：

> **它打算怎么干？现在干到哪了？**

过程日志是「事后」的 —— 用户读到「第 3 步：调了 read_plugin」时，第 4 步已经在跑了。结论是「终局」的 —— 只有完成或失败。中间那段让人最焦虑的时间（尤其十几步的长任务），界面是空的。

## 2. 放在哪，为什么（v2）

```
┌ 会话列表 ┬──────── 对话线程 ────────┬──────── 右栏 296px ────────┐
│ 今天      │ 你 ┃ 把复盘做成…         │ 执行清单 3/5     进行中  ×  │
│ ▸ 会话 1  │ ─────────────────────── │ ▬▬▬▬▬▬░░░░░  3dp 进度条    │
│ ▸ 会话 2  │ ● Trellis 完成 29.0s    │ 01 ✓ 查这周任务数据 1.2s    │
│           │ · 过程 · 4 个动作 …     │ 02 ✓ 整理成四个指标 0.8s    │
│           │                         │ 03 ✓ 生成复盘卡片   4.2s    │
│           │                         │ 04 ● 装到首页并排好         │
│           │                         │    在做什么：deploy         │
│           │  [输入框]               │    会改动：slot.home…       │
│           │                         │    ✓ 可撤销，随时能回退     │
│           │                         │ 05 ○ 核对渲染结果           │
│           │                         │ 本轮没有改动                │
└───────────┴─────────────────────────┴────────────────────────────┘
```

三条位置规则：

1. **首选右栏常驻**：清单回答的是「此刻在干什么」，它必须在场。右栏不随线程滚动，用户眼睛停在结论上也能看见进度。
2. **关掉右栏 ≠ 关掉清单**：换成输入框上方一行常驻摘要（`执行清单 3/5 · 装到首页并排好 · 停止 · 展开`），点哪里都能展开回右栏。常驻、可控，不是「关闭即消失」。
3. **线程里只留一行入口**：`执行计划 · 进行中 3/5 装到首页并排好 ›`，点开右栏。翻历史时一眼能看到「这一轮有几步、结果如何」，但不重复摊开整张清单 —— 否则历史里每轮一张，占满整屏。

为什么不是底部抽屉：会盖住输入框，用户正想插一句话时被挡住。为什么不做浮动胶囊：右栏是「工作现场」，胶囊是「通知」，语义太轻。

## 3. 数据模型

```kotlin
enum class ChatRole { User, Assistant, Step, Status, Plan }
enum class PlanStepState { Pending, Running, Done, Failed, Skipped }

data class PlanStep(
    val text: String,
    val state: PlanStepState = Pending,
    val tool: String = "",          // 宿主在工具开跑时填，模型不用报
    val note: String = "",          // 失败/跳过的一句话原因
    val impact: String = "",        // 这步会改动什么（用户最焦虑的其实不是成败）
    val undoable: Boolean = false,  // 能不能撤销
    val ms: Long = 0L,              // 这步耗时
    val startedMs: Long = 0L,
    val dependsOn: List<Int> = emptyList(), // 依赖第几步；前一步失败 → 自动 Skipped
)

data class ChatLine(…, val plan: List<PlanStep> = emptyList(),
                        val planStartedMs: Long = 0L, val planFinishedMs: Long = 0L)
```

- 清单是**一行** `ChatLine(role = Plan)`，步骤存在 `plan` 里 —— 否则一轮里十行会打散对话节奏，也没法整体折叠/覆盖。
- 落盘走 `ChatStore`（手写 JSON）；重启后勾选状态、耗时、依赖都还在。
- 只允许**一轮一张清单**（`AppRuntime.activePlanId`）。

## 4. 工具契约（模型侧）

| 工具 | 参数 | 什么时候调 |
|---|---|---|
| `set_plan` | `steps: (string \| {title, impact?, undoable?, dependsOn?})[]`，2–12 项，每项 6–18 字、动词开头 | 一件事超过两步时，动手前 |
| `step_done` | `index`（从 0）、`ok`（默认 true）、`note`（失败时写一句为什么） | 每完成一步立刻调，不许攒到最后 |

提示词（`WorkflowTools.guidance`）写死的约束：

1. 简单一问一答不要清单；
2. 步骤写人话，不写内部黑话；`impact` 写清「会改哪个卡片/槽位/插件」；
3. 有依赖就写 `dependsOn`，前一步失败后续会自动跳过；
4. 失败也要调 `step_done(ok=false)`；
5. 清单在右栏，别再在回答里抄一遍；
6. 中途改计划就再调一次 `set_plan`：已完成的步骤按内容保留。

**当前是「约定」，不是「闸」**（2026-10-26 决定）：宿主不拦「没清单就调 deploy 这类写操作」，只靠提示词鼓励。原因是单步活（换配色、停用插件）硬拦会逼模型凑步骤，而 `set_plan` 下限是 2 步；要不要升级成硬约束，等看过实际跑的效果再定。真要加闸时的口径见 §10 的「若改成强制」。

## 5. 状态机

```
set_plan ──► 第一项直接 Running（清单摆好 = 此刻就干这件事），其余 Pending
新工具开始 ──► 第一个 Pending 若还没 Running，则变 Running，并记 tool/startedMs
step_done(i, true)  ──► Done（记 ms），下一个 Pending 变 Running
step_done(i, false) ──► Failed（记 note/ms）；依赖它的 Pending 递归变 Skipped；
                        其余第一个 Pending 变 Running
全部结清 ──► 记 planFinishedMs；右栏 1.5s 后收成「✓ 已完成 N 步 · Xs 展开」
重复调同一步 ──► 「已经记过了」，不改状态
index 越界 ──► 「清单里没有第 N 步」，不抛异常
无清单时 step_done ──► 「这一轮还没有清单，先调 set_plan」
```

取舍：

- **Running 由宿主推断**：不要求模型额外报「开始第 N 步」，少一个工具、少一次调用、少一处偷懒机会。
- **Done/Failed 只由模型报**：宿主只能看到「调了某个工具」，而工具成功 ≠ 这一步目标达成。
- **Skipped 由宿主推导**：依赖失败就不可能再跑，标掉比让它挂着「待做」诚实。
- 异常路径都返回**人话**：会进 `feedback`，模型下一轮能读到并纠正。
- **回合头不撒谎**：清单还有 `Running/Pending` 但这一轮已经不在跑（被打断/崩溃恢复）时，头状态是「中断」而不是「完成」。

## 6. 视觉规格

| 元素 | 规格 |
|---|---|
| 右栏容器 | 296dp 定宽、8dp 圆角、1dp `outlineVariant` 边、`surface` 50% 底；标题行 40dp |
| 标题行 | `执行清单` 等宽小字 0.8sp 字距 + `已结/总数` + 右侧「进行中」（琥珀）/「展开」（收起后）+ `×` |
| 进度条 | 3dp 高，`dataTrack` 作底、`data` 填充，左内边距 12dp |
| 步骤字形 | 18dp 位：Pending 14dp 空心**方框**（不是圆 —— 圆容易被读成单选框）；Running 9dp **琥珀脉冲点**（不是 spinner：转圈是「等待」，脉冲是「在进行」）；Done 14dp 靛实心圆角方块 + 白勾；Failed 14dp 砖红实心 + 白叉；Skipped 虚线空框 |
| 步骤行 | 序号两位等宽 `01`；标题 12.5sp，Done/Skipped 加删除线；元信息 10.5sp 等宽（`完成 · 1.2s` / `正在执行` / `失败 · 原因` / `等待`） |
| 当前步 | 整行 `warningContainer` 底 + 下方展开三行：`这一步在做什么：tool`、`会改动：impact`、`✓ 可撤销，随时能回退` / `· 提交后生效，不能撤销` |
| 底部动作 | 按状态切换：执行中「中止并停止本轮」；有改动「撤销这次改动 / 看差异」；否则「本轮没有改动」 |
| 常驻条（Dock） | 一行：状态字形 + `执行清单 3/5` + 当前步 + `停止`（运行中）+ `展开`；整行可点 |
| 线程入口 | 一行：`执行计划 · 进行中/已完成` + `3/5` + 当前步 + `›`，点击开右栏 |

五态必须**形状 + 颜色双编码**：色弱用户看不出琥珀和靛的区别，但能看出空框、实心勾、实心叉、虚线框的差别。

## 7. 边界（明确不做的）

- **不做树形/嵌套计划**：扁平 2–12 步足够覆盖「查 → 改 → 核对」；嵌套让卡片高度失控，模型也写不好。
- **不从过程日志自动生成清单**：那是「把调用改写成句子」，看着像计划、其实没有计划性。
- **不允许清单里点按钮执行某一步**：步骤是承诺，不是控件，执行权在 agent 手里。
- **不做底部抽屉**：会盖住输入框。
- **不做全局进度环**：`3/5` 文本已经够，环形在右栏太抢。
- **一轮结束清单位置不动、不重排、不删除**：它是这一轮的历史。

## 8. 已知缺口

1. **Running 只有一个**：ToolAgent 目前串行，并行时清单只能显示一个进行中。
2. **暂停/继续没做**：底部「中止」是取消整轮（走 `CancelException`），不是可恢复的暂停。
3. **清单不参与模型上下文**：下一轮它不知道上一轮清单长什么样；「接着上次的计划做」需要写进 state block。
4. **撤销是整轮粒度**：`undoRound` 回滚整轮改动，不能只撤某一步。
5. **Dock 与右栏是同一份状态的两个视图**：没有动画过渡，关右栏是硬切。

## 9. 验证方式

- 单测：
  - `AppRuntimeTest.theWorkPlanSitsUnderTheUsersLineAndTicksOff`（插在用户行下、勾一步亮下一步、失败原因挂步骤、同轮改计划覆盖、重启后状态还在）；
  - `AppRuntimeTest.dependentStepsAreSkippedWhenAnEarlierStepFails`（依赖失败 → 递归 Skipped、耗时与结束时刻落盘）。
- 手工：对话里说「把这周的完成情况做成一页」，观察右栏；点 `×` 看输入框上方是否出现常驻条，再点回右栏。
- 截图：`_shots/app-flow-5.png`（右栏形态，3 完成 + 1 进行中 + 1 待做）、`_shots/app-flow-3.png`（关闭右栏后的常驻条形态）。

## 10. 后续可以长出来的东西

- **若改成强制**（本次决定先不做）：把 `set_plan` 放宽到 1–6 步，然后在工具执行前加闸——`deploy / try_plugin / arrange_cards / set_ui / set_plugin_card / set_theme / disable_plugin / remove_plugin` 在没有活动清单时返回「先 set_plan」；读类工具与 `AgentIntent.Chat` 不设闸；配四个测试（无清单调 deploy 被拒 / 有清单通过 / Chat 不受影响 / 单步清单通过）。
- **可恢复暂停**：暂停时冻结在同一状态、保留已完成步骤；
- **断点续做**：把未完成清单带进下一轮 context；
- **每步单独撤销**：`PlanStep` 记 undo 句柄；
- **用户改清单**：划掉/插入一步，作为「人给 agent 的修正」写回下一轮；
- **失败重试**：点失败步骤旁的「重试」= 给 agent 发一条「第 3 步再试一次」。
